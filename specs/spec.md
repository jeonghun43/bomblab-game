## 001 Bomblab 맛보기 프로토타입

**Feature Branch**: `001-bomblab-taster` | **Created**: 2026-09-30
**Input**: "Bomblab 과제를 위한 기초 지식을 SQL Murder Mystery / Ghost in the SQL data 같은 웹게임으로 자연스럽게 익히게 하고 싶다. 우선 테마 3개를 맛만 볼 수 있게 만들어서 비교해 보겠다."

### 목적
- Bomblab을 처음 접하는 학생이 **gdb 명령을 직접 입력하는 경험**을 통해 레지스터, 호출 규약, 메모리 검사 개념을 체득한다.
- 교수자(사용자)는 **세 가지 세계관 톤**을 직접 플레이해 보고 본 개발에 쓸 테마를 고른다.

> 이후 변경: 006에서 폭탄 해체반 하나만 남김. Stage 0은 006에서 삭제.

### User Scenarios & Testing

#### User Story 1 — 링크로 들어가서 테마를 고른다 (Priority: P1)
학생은 공유받은 링크를 열고, 설치 없이 세 개의 테마 카드 중 하나를 선택해 게임을 시작한다.

**Independent Test**: 링크를 열고 카드를 클릭하면 해당 테마의 인트로 대사와 터미널이 보인다.

**Acceptance Scenarios**
1. **Given** 첫 화면, **When** "폭탄 해체반" 카드를 클릭, **Then** 빨간 경고 톤의 터미널과 인트로가 표시된다.
2. **Given** 게임 화면, **When** "테마 변경"을 누름, **Then** 선택 화면으로 돌아간다.

#### User Story 2 — Stage 0: 레지스터 추적 튜토리얼 (Priority: P1)
학생은 `si`, `i r`, `p $rax`로 명령을 한 줄씩 실행하며 `%rax`의 최종 값을 알아내 답으로 제출한다.

**Acceptance Scenarios**
1. **Given** Stage 0, **When** `break stage0` → `run` → `si` 반복 → `i r rax`, **Then** 레지스터 값이 gdb 형식(`rax 0x2a 42`)으로 출력된다.
2. **Given** 올바른 값을 `answer 42`로 제출, **Then** 해제 연출 + 개념 카드 1장이 열리고 Stage 1이 열린다.
3. **Given** 틀린 값 제출, **Then** 폭발 연출이 나오고 점수가 깎이며 재도전할 수 있다.

#### User Story 3 — Stage 1: phase_1 축소판 (Priority: P1)
학생은 `disas phase_1`로 `mov $0x402400,%esi` → `call strings_not_equal` 패턴을 읽고, `x/s 0x402400`으로 비밀 문자열을 찾아 입력한다.

**Acceptance Scenarios**
1. **Given** breakpoint 없이 틀린 문자열로 `run`, **Then** 폭발한다 (실제 과제의 교훈).
2. **Given** `break phase_1` 후 `run`, **Then** 실행이 phase_1 입구에서 멈춘다.
3. **Given** `x/s 0x402400`, **Then** `0x402400: "..."` 형식으로 문자열이 출력된다.
4. **Given** 올바른 문자열로 실행, **Then** `phase_defused` 연출과 클리어 화면이 나온다.

#### Edge Cases
- 알 수 없는 명령 → gdb처럼 `Undefined command: "foo".  Try "help".`
- 프로그램이 실행 중이 아닐 때 `si`/`i r` → `The program is not being run.`
- 빈 입력으로 `run` → 문자열 불일치로 폭발
- 무한루프 방지: 명령 실행 횟수 상한 (10,000 step)

### Requirements

#### Functional Requirements
- **FR-001**: 시스템은 테마 3종(defuse / detective / ghost)의 선택 화면을 제공해야 한다.
- **FR-002**: 시스템은 AT&T 문법 x86-64 부분집합(mov, lea, add, sub, cmp, test, je, jne, jmp, call, ret, push, pop)을 해석·실행해야 한다.
- **FR-003**: 시스템은 gdb 명령 부분집합(break, run, continue, stepi/si, disas, x/s, x/d, info registers, print $reg, delete)을 지원하고 실제 gdb와 유사한 형식으로 출력해야 한다.
- **FR-004**: 시스템은 게임 명령 `help`, `hint`, `answer <값>`을 지원해야 한다.
- **FR-005**: 각 스테이지 클리어 시 개념 카드 1장을 보여줘야 한다.
- **FR-006**: 폭발 시 점수를 차감하고 재도전을 허용해야 한다.
- **FR-007**: 레지스터 패널이 현재 레지스터 값과 다음 실행될 명령을 표시해야 한다.
- **FR-008**: 퍼즐 내용은 모든 테마가 공유하고, 대사·용어·시각 연출만 테마별로 달라야 한다.
- **FR-009**: 서버 없이 정적 파일만으로 동작해야 한다.

#### Key Entities
- **Level**: id, 어셈블리 원문, .rodata 데이터, 입력 방식(answer / run 입력), 정답 판정, 힌트 2개, 개념 카드
- **Theme**: id, 이름, 인트로/클리어/폭발 대사, 용어 치환(예: "개념 카드" → "해체 매뉴얼")
- **CPU State**: 레지스터 16개, ZF/SF/OF/CF, 메모리 맵, rip, breakpoints

### Success Criteria
- **SC-001**: 처음 보는 학생이 15분 이내에 두 스테이지를 모두 클리어한다.
- **SC-002**: 플레이 과정에서 `break`, `run`, `disas`, `x/s`, `i r`, `si` 여섯 명령을 최소 1회씩 사용하게 된다.
- **SC-003**: 교수자가 세 테마를 각각 5분 이내에 체험하고 비교할 수 있다.

### Out of Scope (다음 이터레이션)
- Stage 2 이후 (반복문, switch, 재귀, 연결 리스트)
- 진도 저장, 서버, 로그인, 랭킹
- 모바일 최적화 강화, 사운드

## 002 캐릭터와 장소가 있는 장면 진행

**Feature Branch**: `002-story-scenes` | **Created**: 2026-09-30
**Input**: "터미널만 있는 게 아니라 캐릭터나 장소가 있고, 게임처럼 화면이 바뀌는 걸 원했다. SQL Murder Mystery나 Ghost in the SQL data처럼." 추가 결정: 테마 3개 모두 짧게, 대사 진행과 클릭 조사를 섞는다, 픽셀 아트.

### 배경
001(맛보기)은 gdb 터미널과 퍼즐 엔진을 검증했다. 하지만 화면이 터미널 하나뿐이라 게임이라기보다 실습 도구처럼 느껴진다. 002에서는 퍼즐 엔진은 그대로 두고, 그 위에 **장소 → 대화 → 조사 → 컴퓨터(터미널) → 다음 장소**로 이어지는 게임 층을 얹는다.

### User Scenarios & Testing

#### User Story 1 — 장면과 캐릭터 (Priority: P1)
학생이 테마를 고르면 픽셀 아트로 그린 장소가 나오고, 캐릭터 초상화와 대사창으로 이야기가 진행된다.

**Acceptance Scenarios**
1. **Given** 테마 선택, **When** 게임 시작, **Then** 장소 이름 카드가 뜬 뒤 첫 장소 배경이 보이고 캐릭터가 말을 건다.
2. **Given** 대사가 타이핑되는 중, **When** 클릭(또는 Enter/Space), **Then** 문장이 즉시 완성되고, 한 번 더 누르면 다음 대사로 넘어간다.

#### User Story 2 — 조사 (Priority: P1)
조사 단계에서는 장소 안의 사물을 클릭해 살펴보고 단서를 얻는다. 단서 중 일부는 퍼즐에 필요한 개념(레지스터, 호출 규약)을 세계관 안의 물건(매뉴얼, 포스트잇, 벽보)으로 가르친다.

**Acceptance Scenarios**
1. **Given** 조사 단계, **Then** 클릭할 수 있는 사물이 표시되고 목표 문구("차량 안을 조사하자 1/2")가 보인다.
2. **Given** 사물 클릭, **Then** 관련 대사가 나오고 단서가 수첩에 추가된다.
3. **Given** 필요한 단서가 모자란 상태에서 컴퓨터 클릭, **Then** 캐릭터가 "먼저 ~부터 보자"라고 막는다.

#### User Story 3 — 장면 속 컴퓨터로 퍼즐 풀기 (Priority: P1)
장면 속 컴퓨터(노트북, CRT, 분석용 PC)를 클릭하면 모니터 틀 안에 001의 gdb 터미널이 열린다. 퍼즐을 풀면 터미널이 닫히고 이야기가 이어진다.

**Acceptance Scenarios**
1. **Given** 컴퓨터 클릭, **Then** 모니터 오버레이에 터미널, 레지스터, 디스어셈블리가 열린다.
2. **Given** 퍼즐 해제, **Then** 개념 카드가 나오고, 닫으면 장면으로 돌아와 다음 대사가 이어진다.
3. **Given** 폭발, **Then** 001처럼 감점과 연출이 나오고 캐릭터가 한마디 한다. 터미널은 열린 채 재도전할 수 있다.

#### User Story 4 — 퀴즈 선택지 (Priority: P2)
두 퍼즐 사이에 캐릭터가 개념 퀴즈를 낸다(예: "두 번째 인자는 어느 레지스터?"). 틀리면 캐릭터가 설명해 준다.

#### Edge Cases
- 터미널이 열려 있을 때 Enter는 터미널 입력으로만 쓰이고 대사를 넘기지 않는다.
- 이미 조사한 사물을 다시 클릭하면 짧은 대사만 나오고 단서는 중복되지 않는다.
- 폰 폭(375px)에서는 장면이 화면 폭에 맞게 줄고, 대사창은 장면 아래에 붙는다.

### Requirements
- **FR-001**: 테마마다 장소 2곳, 캐릭터 1명(초상화)이 있어야 한다.
- **FR-002**: 배경과 초상화는 코드로 그린 픽셀 아트여야 한다. 외부 이미지는 쓰지 않는다.
- **FR-003**: 장면에는 가벼운 움직임이 있어야 한다(LED 깜빡임, 비, 형광등 깜빡임 등).
- **FR-004**: 이야기는 데이터(대본)로 정의하고, 대본 실행기가 say, scene, investigate, quiz 단계를 처리해야 한다.
- **FR-005**: 조사 사물은 look(대사와 단서), terminal(퍼즐 열기), exit(다음 장소로) 세 종류를 지원해야 한다.
- **FR-006**: 001의 퍼즐 엔진(engine/, levels.js)과 테스트를 수정 없이 재사용해야 한다.
- **FR-007**: 수첩(단서 목록)과 개념 카드를 HUD에서 언제든 열어 볼 수 있어야 한다.

### Success Criteria
- **SC-001**: 한 테마를 처음부터 끝까지 10~15분 안에 마친다.
- **SC-002**: 터미널 밖(장면, 조사, 퀴즈)에서 보내는 시간이 전체의 절반쯤이 되어 "게임을 한다"는 느낌을 준다.
- **SC-003**: 학생이 퍼즐 전에 조사 단서로 필요한 개념을 한 번 보고 들어간다.

### Out of Scope
- 테마별 두 번째 캐릭터, 분기 엔딩, 사운드, 저장
- Stage 2 이후 퍼즐

## 003 처음 보는 학생을 위한 튜토리얼

**Feature Branch**: `003-onboarding-tutorial` | **Created**: 2026-09-30
**Input**: "Bomblab을 처음 접하는 참가자는 gdb가 뭔지, 레지스터가 뭔지 하나도 모른다. 다짜고짜 lea나 eax 이야기를 하면 뇌정지가 온다. 지식의 공백을 이용해 호기심을 자극하고, 튜토리얼로 필수 기초를 익히게 하고 싶다." 결정: 폭탄 해체반 한 이야기에 먼저 적용하고, 플레이 시간은 15~20분.

### 문제
002의 대본은 첫 장면부터 `lea`, `%eax`, AT&T 문법 같은 용어를 설명 없이 쓴다. 배경지식이 없는 학생은 첫 장소에서 이해를 포기한다.

### 설계 원칙
1. **현상 먼저, 이름은 나중에.** 칸의 숫자가 바뀌는 걸 먼저 보여 주고, 그다음에 "레지스터"라는 이름을 붙인다.
2. **한 장면에 새 단어 하나.** `lea`는 다루지 않는다. `%esi`나 `%eax`는 실제로 마주쳤을 때 "rsi/rax의 다른 이름"이라고 한 줄로 설명한다.
3. **비유로 연결한다.** 레지스터는 CPU 작업대의 칸, 메모리와 주소는 창고와 사물함 번호, 함수 호출은 심부름(1번 주머니 rdi, 2번 주머니 rsi, 결과는 rax)이다.
4. **도구는 필요해진 순간에 준다.** 명령어는 하나씩 열리고, 아직 배우지 않은 명령은 막힌다.
5. **예측하고 확인한다.** 한 줄을 실행하기 전에 결과를 먼저 고르게 한다.
6. **도움은 점점 줄인다.** 초반에는 입력칸에 다음 명령이 흐리게 보이고, 마지막 과제에서는 목표만 준다.
7. **호기심의 공백을 만든다.** 해독기가 폭탄 코드를 처음부터 보여 주되 거의 다 가려 둔다. `explode_bomb` 한 단어만 읽힌다. 개념을 배울 때마다 가려진 부분이 풀리고, 마지막에 100%가 된다.

### User Scenarios & Testing

#### US1 — 훅: 터지는 경험과 가려진 코드 (P1)
학생은 폭탄 복제본을 `run`으로 실행하고 아무 글자나 넣어 터뜨린다(감점 없음). 이어서 해독기가 열리는데, 코드는 대부분 ▒로 가려져 있고 `explode_bomb`만 읽힌다.
- **Given** 첫 과제, **When** `break`를 입력, **Then** "아직 안 배운 도구"라며 막힌다.
- **Given** 폭발, **Then** 점수는 깎이지 않고 해독기가 해독률 0% 상태로 열린다.

#### US2 — 시간 정지 (P1)
`break`와 `continue`를 얻고, phase_1에서 멈추는 경험을 한다.

#### US3 — 작업대 칸 (P1)
훈련용 계산기(mov, add, sub만 씀)를 한 줄씩 실행한다. 레지스터 패널이 이때 처음 나타나고, 칸은 rax와 rdi만 보인다. 예측 퀴즈를 두 번 풀고 결과를 `answer`로 제출한다.
- **Given** `si`로 `mov $0x5,%rax` 실행, **Then** rax 칸이 5로 바뀌며 강조되고, 다음 과제로 넘어간다.

#### US4 — 사물함 번호 (P1)
`x/s`로 주소 안의 글자를 읽는다. `p $rdi`로 큰 숫자를 본 뒤, 그 숫자가 자기 입력이 들어 있는 주소임을 발견한다.

#### US5 — 심부름과 실전 (P1)
서버실 벽보로 인자와 반환값을 배우고, `disas`를 얻는다. 목표만 보고 폭탄을 해체한다. 해독기가 100%가 된다.

#### US6 — 용어 풀이 (P2)
대사 속 밑줄 단어를 누르면 쉬운 말 풀이가 뜬다.

#### Edge Cases
- 과제와 상관없는 명령(단, 배운 명령)은 그대로 실행되고, 과제는 유지된다.
- 레슨 도중 터미널을 닫았다가 다시 열면 그 과제부터 이어서 한다.
- 예측 퀴즈가 떠 있는 동안 명령을 치면 "먼저 위 질문에 답해 봐"라고 안내한다.
- 폭탄 해체반 외의 이야기는 명령 잠금 없이 002처럼 동작한다.

### Requirements
- **FR-001**: 대본에 레슨(과제 목록)을 넣을 수 있어야 하고, 과제 달성 조건은 데이터(event, reg, cmd, answer, running)로 표현한다.
- **FR-002**: 튜토리얼 이야기에서는 배운 명령만 실행할 수 있어야 한다. `help`는 배운 명령만 보여 준다.
- **FR-003**: 레지스터 패널, 보이는 칸, 디스어셈블리 패널이 과제에 따라 단계적으로 나타나야 한다.
- **FR-004**: 해독기는 phase_1 코드의 모든 토큰을 개념에 연결하고, 배운 개념만 보여 주며, 해독률을 표시해야 한다.
- **FR-005**: 예측 퀴즈와 확인 버튼(ack) 과제를 터미널 위쪽 캐릭터 줄에서 지원해야 한다.
- **FR-006**: 대사의 `[[용어]]`는 눌러서 풀이를 볼 수 있어야 한다.
- **FR-007**: 훅과 연습 단계의 폭발에는 감점이 없어야 한다. 카운트다운은 마지막 실전에서만 돈다.
- **FR-008**: 튜토리얼에서는 `lea`와 32비트 레지스터 이름을 먼저 꺼내지 않는다(계산기는 64비트 이름만 쓴다).

### Success Criteria
- **SC-001**: gdb와 어셈블리를 처음 보는 학생이 15~20분 안에 끝낸다.
- **SC-002**: 모든 새 용어는 그 현상을 먼저 보여 준 뒤에 이름이 나온다(대본 리뷰로 확인).
- **SC-003**: 끝낸 학생이 run, break, continue, si, p, x/s, disas를 각각 스스로 한 번 이상 입력했다.

### Out of Scope
- 탐정·유령 이야기의 튜토리얼화(다음 이터레이션) — 006에서 두 이야기를 삭제하며 종료

## 004 반장 구어체 말투

**Feature Branch**: `004-banjang-voice` | **Created**: 2026-10-01
**Input**: "말투가 너무 AI스럽다. ~다, ~한다 말고 반장이 신입한테 이야기하듯 구어체로 싹 다 바꿔 줘. 후보를 보여 주고 내가 고른 종결어미를 쓰자."

### 사용자가 고른 종결어미
| 상황 | 쓸 말투 |
|---|---|
| 설명할 때 | ~하는 거야 / ~인 거지, ~하거든 / ~잖아, ~란 말이지 / ~라고, ~해 / ~이야 |
| 시킬 때 | ~해 보자 / ~하자, ~해 볼래?, ~하면 돼 |
| 물어볼 때 | 신입, 너 생각은 어때?, ~일까? / ~인 것 같아? |
| 반응할 때 | 좋아, 잘했어! / 거봐, 내가 뭐랬어 / 괜찮아, 다시 해 보자 |

고르지 않은 것: "~해 봐", "알겠지? / 맞지?", "~할 수 있겠어?", "오, 제법인데?"

> 이후 변경(005): 사용자가 "~해 / ~이야"를 직접 추가함. 처음에는 고르지 않은 목록에 있었음. "~거든"은 한 대사에 한 번까지.

### Requirements
- **FR-001**: 폭탄 해체반의 반장이 하는 모든 말(대사, 과제 대사, 예측 질문과 정답·오답, 퀴즈, 폭발, 오답, 잠긴 도구)을 위 종결어미로 바꾼다.
- **FR-002**: 목표 문구와 힌트도 "~다"로 끝내지 않는다(목표는 "~하자", 힌트는 "~하면 돼").
- **FR-003**: 용어 풀이와 해독기 설명도 반장 말투로 바꾼다. 둘 다 교육 내용이므로 대본 md로 옮긴다(`## 용어`, `## 해독기 풀이`).
- **FR-004**: 내레이션 줄은 반장 대사로 바꾼다. 확인 버튼(신입의 말)은 반장에게 하는 존댓말("터졌어요…")로 바꾼다.
- **FR-005**: 고른 종결어미를 `scripts/defuse.md`의 `## 말투` 섹션에 기록해 앞으로 대본을 고칠 때 기준으로 삼는다.
- **FR-006**: 교육 순서, 과제 조건, 퀴즈 정답은 바꾸지 않는다.

### Success Criteria
- **SC-001**: defuse.md의 반장 대사, 목표, 힌트, 용어 풀이, 해독기 설명 중 "~다."로 끝나는 문장이 없다(인용문 제외). 테스트로 검사한다.
- **SC-002**: 기존 테스트와 레슨 모범답안 시뮬레이션이 모두 통과한다.

### Out of Scope
- 탐정·유령 이야기(반장이 아닌 캐릭터이고 튜토리얼 준비 중)

## 005 남은 글을 md로 모으기

- **FR-004**: md로 옮긴 결과는 옮기기 전과 화면에 보이는 내용이 같아야 한다. 계산기 카드의 "~한다" 문장 하나만 고친다.
- **FR-005**: 코드에 남는 글(시스템 안내, 선택 화면 문구, 프로그램 출력)은 GUIDE.md에 위치를 적는다.
